# PDF 문항 하단 범위 수정: 실제 구현과 검증

2026-09-18. 이번 변경은 등록 범위 오류에 대한 수정이다. 필기 제거 모델을 추가하거나 전체 문항 분리 정확도를 검증한 작업은 아니다.

## 확인한 입력

사용자가 지정한 PDF의 **현재 6쪽 버전**을 `output/content-bounds/input.pdf`로 고정했다. SHA-256은 `edda5bff478f81e078ace1baaa56f829ed2a033e975c136c360b500b9910ff39`이다. 이전 작업에서 읽었던 같은 경로의 7쪽 파일과 바이트가 다르므로 그 결과와 비교하지 않았다. 수정 전 trace인 `before-fix.json`과 수정 후 trace의 해시가 같은지 비교 스크립트가 검사한다.

## 실제 호출 경로

| 순서 | 실행 코드 | 실제 동작 |
|---|---|---|
| 입력 | `app/questions/new/page.tsx`의 `ingest` | 파일을 `importDocument`에 전달 |
| PDF 렌더링 | `lib/documents/import.ts`의 `importDocument` | PDF.js로 페이지 렌더링, 텍스트 run 추출, 원본 PDF와 페이지 이미지 유지 |
| 물리적 후보 | 같은 파일의 내부 `analyze` → `analyzePixels` → `analysis.worker.ts` → `physical.ts`의 `physicalRegions`, `neutralPixels` | 세로선 등의 영상 규칙으로 읽기 구역 추정, 분석용 대비 조절. 저장할 컬러 원본은 변경하지 않음 |
| OCR | `usableText` 실패 시 `ocr.ts`의 `recognizeRegions` | Tesseract.js 7, LSTM `kor+eng` best_int 언어 데이터. 각 구역에 AUTO(3), SPARSE_TEXT(11) 두 번 실행. 후자는 문항 시작 표기 보완에 사용 |
| 문항 후보 구성 | `segment.ts`의 `segmentDocument` | 텍스트 줄에서 번호 anchor를 찾고 다음 anchor 또는 단 끝까지 구역 생성. 공통 자료/이어짐 후보 유지 |
| 이번 추가 | `content-bounds.ts`의 `assessContent`, `withContentBounds` | 넓은 탐색 범위와 본문 끝 제안 분리. 제안은 자동 저장 범위로 적용하지 않음 |
| 검토 화면 | `components/documents/document-review.tsx`의 `DocumentReview` | 실선은 현재 `fragment.rect`, 즉 **실제 저장 범위**. 회색 점선은 `candidateRect`, 주황 점선은 미적용 제안. 적용/원본 유지/수동 조절 가능 |
| 이미지 생성 | `DocumentReview.accept` → `compose.ts`의 `composePiece` | 각 fragment의 `rect`로 원본 페이지를 canvas crop하여 별도 PNG 생성. 여러 쪽을 거대 이미지로 이어 붙이지 않음 |
| 영구 저장 | 등록 페이지 `save` → `lib/db.ts`의 `saveQuestions` | IndexedDB에 원본 문서·페이지·조각 Blob·문항·자료 관계를 저장 |

현재 파일의 6쪽 모두 텍스트 추출 대신 OCR 경로를 실행했다. 외부 AI API, 문항/필기 객체 탐지 모델, 신경망 레이아웃 모델, 필기 분류기는 **실행되지 않는다**. `registration-graph.ts`의 설계 자료 전체가 자동 관계 추론기로 실행된다고 해석하면 안 된다. 현재 자동 관계는 규칙 후보이며 검토자가 확인한다.

## 중간 결과와 좌표

- 원시 결과: 각 OCR pass의 **텍스트 줄**과 bbox. 별도 문제 콘텐츠 객체 탐지 단계는 없다. `ocrPasses`를 이번에 추가하여 sparse 필터 이전 결과도 저장한다.
- 묶은 결과: `segmentDocument`가 만든 문항별 넓은 구역. 수정 전에는 이것이 바로 화면/저장 범위였다. 별도 본문 끝 정밀화 단계가 없었다.
- 최종 결과: 검토 후 `fragment.rect`, 실제 화면 캡처, IndexedDB에서 읽은 저장 PNG. `before.json`, `after.json`, `verification.json`에 저장한다.
- 페이지 이미지: 모든 페이지 **1821 × 2580 px**. 분석용 canvas와 저장 원본 페이지는 동일 크기다. OCR 입력은 각 읽기 구역으로 잘라낸 약 765 × 2451 px 이미지이며 정확한 구역 좌표는 trace에 있다.
- `rect`와 OCR 줄 좌표: 회전 적용된 페이지 이미지 좌상단 기준, x/y/w/h를 각각 페이지 너비/높이로 나눈 0~1 좌표. 화면 CSS도 같은 비율을 사용한다.
- 원본 PDF 사용자 좌표와 렌더링 픽셀 사이에는 PDF.js viewport의 3×3 `sourceToAnalysis` 및 역행렬을 저장한다. 이 파일은 페이지에 따라 `[0,2.5,0;2.5,0,0;0,0,1]` 또는 `[0,-2.5,1821;-2.5,0,2579.4;0,0,1]`이다. 정수 canvas 높이와 viewport 소수 높이는 구별한다.
- 최종 PNG 너비/높이는 `round(rect.w*1821)`, `round(rect.h*2580)`이다. 같은 원본과 rect로 브라우저에서 다시 crop해 저장 PNG와 픽셀 단위 비교한다.

## 입증된 원인

### 1. 다음 문제까지의 탐색 구역을 실제 저장 범위로 사용

수정 전 `segmentDocument`는 `y = line.y - .005`, `end = next.line.y - .005`(마지막이면 단 끝)로 만들었다. `DocumentReview`와 `composePiece`가 모두 이 rect를 그대로 사용했다.

첫 쪽 1번은 원시 OCR의 여러 작은 본문/필기 줄로 인식되지만, 묶음 결과는 `y=0.18589147, h=0.36937984`이다. 다음 2번 시작점까지의 풀이 전체를 포함한다. 이는 본문과 필기를 하나의 객체로 탐지한 결과도, 수동 영역 합치기 결과도 아니다. **묶음 단계의 범위 정의** 때문이다.

### 2. 별도 OCR 줄로 나온 분수 분자가 시작 경계 위에서 잘림

1번 본문 anchor의 y는 약 0.19089147이고 분수 분자는 y≈0.18275194에 별도 줄로 나온다. 종전 시작 y≈0.18589147은 분자 상단을 자른다. `startYs`를 계산할 때 같은 단에서 anchor 행과 세로로 겹치는 줄들의 가장 위쪽까지 포함하도록 최소 수정했다. 본문 아래를 줄이는 변경과 별개의, 원시 OCR로 확인한 기존 잘림이다.

### 배제한 원인 및 한계

이번 확인 사례에서 좌표 왕복과 화면/저장 픽셀 비교는 일치했다. 따라서 큰 하단 범위의 원인은 회전·배율 변환 오류가 아니다. 다만 이것으로 모든 PDF의 변환 정확성을 보증하지 않는다. 흑백 필기와 인쇄물은 원시 OCR부터 섞여 있으며, 현재 구성에는 이를 안전하게 구별하는 분류가 없다.

## 최소 수정 내용

- `Fragment.candidateRect`는 탐색 범위, `rect`는 선택한 실제 저장 범위다. 저장 메타데이터에도 둘 다 남긴다.
- 지시문 끝과 명시적 `[n점]`이 함께 인식될 때만 본문 끝 **검토 제안**을 만든다. 끝 행에 걸친 큰 수식 줄은 포함하고 줄 높이에 비례한 여유를 둔다.
- 그림·보기·표·도형·답안란·이어짐 단서가 있거나 근거가 부족하면 넓은 원본을 유지한다. 특정 페이지, 학교, 문항 번호, 고정 절단 높이를 사용하지 않는다. 흰 공간 제거도 하지 않는다.
- 제안은 내용 판단의 보증이 아니다. 배점 아래에 선택지나 그림이 있을 수 있으므로 자동 확정하지 않고 **본문 끝 제안 적용**을 누른 뒤 항목 확인을 거친다.
- 경계 상태 `unresolved/proposal/chosen/manual/kept`와 필기 상태 `not-separated`를 별도로 표시한다. 적용 후에도 붉은 동그라미처럼 본문과 겹친 필기는 남는다. 인쇄물을 추측해 복구하지 않는다.
- 공통 지문, material/dependency ID, 조각 순서, 여러 페이지 조각은 변경하지 않는다. 자료·이어짐 조각은 이 규칙으로 축소하지 않는다.
- 원본 유지 버튼으로 복원할 수 있다. 수동 수정 시 이전 제안을 승인한 것으로 처리하지 않는다.
- 실제 페이지 전환 중 이전 Blob URL을 반환하던 `useBlobUrl`도 수정했다. 현재 Blob과 일치하는 URL만 반환하며 기존 URL은 effect cleanup에서 해제한다.

## 검증과 남은 실패

수치 및 원본/수정 이미지: `output/content-bounds/report.html`, `comparison.json`.

| 사례 | 수정 전 → 저장 PNG (px) | 결과 |
|---|---|---|
| 1번 | 765×953 → 765×147 | 높이 84.6% 감소, 분자 상단 보존, 겹친 빨간 필기 잔존 |
| 서술형 4번 | 765×1056 → 765×180 | 높이 83.0% 감소, 본문·수식 보존 |
| 2번 | 765×951 → 동일 | 근거 부족, 미해결 |
| 13번 | 765×978 → 동일 | 삼각형과 본문 유지, 필기 잔존 |
| 17번 | 765×1160 → 동일 | 근거 부족, 미해결 |
| 4번 | 765×92 → 동일 | 잘못된 70번 시작점으로 인한 기존 불완전 분리 |

선택한 6개 저장 조각의 픽셀 채널 불일치는 모두 0, 화면 rect 일치 검사는 통과했다. 원본↔분석 좌표 왕복 최대 오차는 4.69×10⁻¹³ px이다. 브라우저 pageerror는 0건이었다.

브라우저 검증은 6개 사례를 선택해 UI에서 제안 적용 또는 원본 유지를 수행하고 IndexedDB에 저장한다. 화면 스타일과 저장 rect의 일치, 원본에서 다시 생성한 crop과 저장 PNG의 픽셀 일치를 검사한다. 테스트의 확인 체크박스 클릭은 저장 경로 검증용이며, 모든 문항의 의미상 완전성을 승인한 것이 아니다.

- 1번: 하단 풀이를 줄이고 별도 분수 분자 상단을 보존했다. 빨간 필기 일부는 남는다.
- 서술형 4번: 지시문·수식·배점 아래 풀이 영역을 줄였다. 이 항목은 풀이를 쓰라는 문항이므로 새 시험지의 풀이 공간은 출력 설정에서 별도로 제공한다. 원본 유지도 가능하다.
- 2번·17번: 본문 끝 근거가 부족해 넓은 범위를 유지했다. **미해결 사례**다.
- 13번: 그림 참조가 있어 하단을 줄이지 않고 도형을 보존했다. 필기 영역도 남는다.
- 4번: 수식 일부를 `70번` anchor로 오인하여 문항이 잘못 나뉜 **기존 실패가 남는다**. 자동 검출 완전성을 통과했다고 보고하지 않는다. 검토 화면에서 두 영역을 합쳐 확인할 수 있다. 이번 변경으로 해결한 것으로 계산하지 않는다.

타입 검사, 단위 테스트 33개, 프로덕션 빌드를 실행했다. 실제 PDF의 전후 조각을 시각적으로 확인한다. 전체 22문항에 대한 정답 라벨 기반 완전성 평가, 이 PDF에 없는 국어·영어 장문/페이지 이어짐의 실제 문서 검증, 프린터 인쇄는 이번 수정에서 실행하지 않았다. 공통 자료/여러 조각 관계 보존은 단위 테스트로만 회귀 확인했다.

## 재현

```sh
npm run typecheck
npm test
npm run build
npm run start -- --port 3028
node scripts/verify-content-bounds.mjs '/절대경로/입력.pdf'
node scripts/render-content-evidence.mjs
```

브라우저 검증 스크립트는 해당 감사 PDF 사례의 번호를 선택하지만 제품 분석기는 이 번호를 사용하지 않는다. 실행 전 최초 수정 전 진단 JSON을 `output/content-bounds/before-fix.json`으로 보관해야 한다. 다른 PDF로 비교할 때 이 파일도 같은 입력의 수정 전 결과로 교체해야 하며, 스크립트가 다른 해시의 비교를 거부한다. PNG/JSON/PDF 증거는 개인 자료를 포함하므로 git에서 제외된 output 폴더에만 남긴다.
